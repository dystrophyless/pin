# Saved agenda read views

`/today` and `/week` read saved plan occurrences for the owner and use the profile's home time zone. A day is the half-open interval between consecutive local midnights. A week begins Monday and spans seven local dates. Those local boundaries are converted independently to UTC, so spring-forward and fall-back days keep their actual 23- or 25-hour length. Timed entries keep their event-zone date and time in the row, and the event zone is shown when it differs from the profile zone.

The query returns scheduled, overdue, untimed, and optionally completed entries. Cancelled entries are excluded. Ongoing appointments remain scheduled until their end instant; just-ended appointments enter Overdue when `ends_at < now`. Timed tasks enter Overdue when `starts_at < now`; deadlines when `deadline_at < now`; older untimed entries when their stored local date is before today's date in the profile zone. Untimed rows show their saved date and title without inventing a time or changing persisted state. Overdue open entries remain visible even when their original date is before the requested interval. Completed entries appear only when the optional completed view is enabled.

Recovery reads use the Planning-owned `AgendaReadStore.list_overdue(owner_id, *, as_of, display_zone, limit=100, for_update=False)` contract. It returns native `AgendaRecord` rows for open appointments whose `ends_at`, deadlines whose `deadline_at`, and timed tasks whose `starts_at` are at or before `as_of`; untimed tasks are overdue when their stored date is before the current date in `display_zone`. Ongoing appointments, completed and cancelled rows, and rows owned by another user are excluded. Results are ordered oldest overdue first with occurrence ID as the stable tie-breaker, and `limit` must be between 1 and 1,000. The reader uses the caller's session without committing and reads current Planning rows independently of reminder schedules or delivery attempts, so tasks without reminders remain eligible. Recovery callers may set `for_update=True` after locking the owner's preferences; the reader fixes bounded membership, locks the selected plan rows and then occurrence rows in stable ID order, and rereads their current state/title while those locks remain held through the caller's transaction.

The owner-scoped query builds an ordered snapshot of occurrence IDs and stores page starts for 24 hours. Snapshot membership/order stays fixed while navigating, but each page reloads current owner-scoped records and checks current state and interval eligibility. Therefore title/details updates appear on later pages, while cancelled or newly excluded completed records disappear. Each command and agenda callback checks published Billing `VIEW_PLAN` access in the same worker session before querying/creating snapshots or rendering rows. The existing policy allows expired, non-deleted accounts to view saved plans and denies deleted accounts. Callback tokens are opaque, owner-bound, single-use, and expire after the Telegram callback TTL; a replay by another owner is rejected. Invalid, expired, replayed, and stale callbacks receive the current onboarding recovery plus localized guidance to send `/today` or `/week`; user-supplied callback data is not included in that message. Expired snapshots are removed opportunistically for the same owner when a new agenda opens; there is no background cleanup job.

The Telegram presentation API is pure: `render_agenda(page, language="ru" | "en") -> AgendaReply`. `AgendaReply` contains `markdown` (escaped Telegram MarkdownV2 text), `plain_text` (equivalent text without Markdown escaping), `buttons` (a tuple of `AgendaButton(text, action, value)` keyboard inputs), and `handling`. Each page stays below the 3,900 UTF-16-unit application budget, leaving room under Telegram's message limit. Page callbacks carry a snapshot UUID and integer offset; completed-view buttons carry the view and enabled flag. Callback payloads are checked against Telegram's 64-byte limit before use. The empty state is localized and still offers the completed-view toggle.

## Verification boundary

`tests/test_agenda.py` covers local interval construction, DST lengths, Monday start, half-open boundaries, overdue classes, owner fence behavior in the in-memory contract, snapshot pagination/update semantics, empty RU/EN rendering, and rejection of unknown callback actions by the version map. `tests/test_agenda_postgres.py` exercises exact PostgreSQL membership IDs, two-owner isolation, event-zone crossing, appointment overlap/end behavior, task/deadline/untimed overdue classification, DST UTC boundaries, durable pagination, stale-owner replay, page updates/expiry, worker receipt/outbox atomicity, expired-account view access, deleted-account denial for both commands and callbacks, and settings-draft/profile-version callback behavior. It also proves that default overdue reads do not block row updates, locked recovery reads hold selected plan/occurrence rows until caller commit, and changes committed between membership selection and locking are reread. It asserts that agenda view handling creates no usage reservations. It requires `PIN_TEST_AGENDA_DATABASE_URL` pointing at a fresh owned `pin_issue9_*` database and verifies the configured PostgreSQL cluster before running migrations.

Pure renderer output tests establish the localized strings, message-length budget, and keyboard input shape. Actual empty/long Telegram delivery qualification and user dialogue/owner acceptance remain core-gate work; these local tests do not claim production Telegram delivery or acceptance.

Local verification was run on 2026-10-14: 16 targeted agenda tests passed, including all six guarded PostgreSQL tests for snapshot behavior, access rules, and callback versions; the seven existing onboarding PostgreSQL regressions also passed against the same owned fixture. Ruff and targeted mypy passed.
